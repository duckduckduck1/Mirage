# Как контрибьютить в Mirage

Этот документ описывает рабочий процесс: как вести ветки, оформлять коммиты и
готовить pull request. Цель — чистая, читаемая история и дисциплина, как в
зрелых инженерных командах. Даже если над проектом работает один человек, эти
правила тренируют культуру DevOps и красиво выглядят в истории.

Документация подчиняется отдельному [style guide](docs/style-guide.md).

## Рабочий процесс с ветками

Модель — **trunk-based lite**:

- `main` — всегда рабочая (зелёная) ветка. Прямой push в `main` запрещён, только
  через pull request.
- Любое изменение делается в короткоживущей ветке от свежего `main`.
- Ветку называем по схеме `тип/краткое-описание` латиницей через дефис:
  - `feat/subscription-domain`
  - `docs/architecture`
  - `fix/ufw-rule-order`
  - `chore/update-gitignore`

```bash
git switch main
git pull
git switch -c docs/architecture   # создать ветку и перейти в неё
```

## Коммиты — Conventional Commits

Каждое сообщение коммита следует формату
[Conventional Commits](https://www.conventionalcommits.org):

```
тип(область): краткое описание

[необязательное тело: что и почему, перенос на 72 символа]

[необязательный футер: ссылки на задачи, BREAKING CHANGE]
```

### Типы

| Тип        | Когда использовать |
|------------|--------------------|
| `feat`     | новая функциональность |
| `fix`      | исправление бага |
| `docs`     | только документация |
| `chore`    | рутина: конфиги, зависимости, скелет |
| `refactor` | переработка без смены поведения |
| `ci`       | пайплайны CI/CD |
| `infra`    | инфраструктура: Terraform, Ansible, Docker |
| `test`     | тесты и проверки |

### Правила сообщения

- **Область (scope)** — необязательна, но желательна: затронутый компонент
  (`xray`, `mtg`, `ufw`, `terraform`, `architecture`).
- **Описание** — в повелительном наклонении, с маленькой буквы, без точки в конце.
  Хорошо: `add migration design`. Плохо: `Added migration design.`
- Длина первой строки — до ~72 символов.
- Одно логическое изменение = один коммит.

### Примеры

```text
docs(architecture): добавить дизайн миграции без потерь
chore: инициализировать скелет репозитория
infra(terraform): описать VPS и firewall-правила
fix(ufw): открыть порт панели после установки 3x-ui
```

## Pull request

1. Запушь ветку и открой PR в `main`.
2. Заполни [шаблон PR](.github/pull_request_template.md): что меняем, зачем, как
   проверено.
3. Дождись зелёных проверок (когда появится CI).
4. Сделай squash-merge, чтобы в `main` попал один аккуратный коммит.

### Чек-лист перед PR

- [ ] Ветка создана от свежего `main`.
- [ ] Коммиты по Conventional Commits.
- [ ] Документация обновлена и соответствует [style guide](docs/style-guide.md).
- [ ] **В коммиты не попали секреты** (ключи, пароли, `.env`, состояния Terraform).
- [ ] Значимое решение зафиксировано в [ADR](docs/adr/), если оно архитектурное.
