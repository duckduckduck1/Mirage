# Как контрибьютить в Mirage

Этот файл описывает рабочий процесс для изменений в репозитории.

## Ветки

Модель веток:

- `main` — стабильная production-ветка;
- `dev` — интеграционная ветка перед `main`;
- короткоживущие ветки создаются от свежего `dev`.

Прямой push в `main` и `dev` не используется. Обычный PR идёт из рабочей ветки в
`dev`. Выпуск идёт отдельным PR из `dev` в `main`.

Пример:

```bash
git switch dev
git pull --ff-only origin dev
git switch -c docs/product-documentation
```

После merge короткоживущая ветка удаляется локально и на GitHub.

## Коммиты

Сообщение коммита пишется по Conventional Commits:

```text
тип(область): краткое описание
```

Правила:

- описание на русском языке;
- повелительное наклонение;
- маленькая буква после двоеточия;
- без точки в конце;
- один коммит фиксирует логически завершённое действие конкретной ветки.

Примеры:

```text
docs(readme): обновить быстрый старт
feat(admin): добавить проверку уведомлений
fix(xui): исправить сбор профиля
```

## Pull request

1. Запушь ветку.
2. Открой PR в `dev`.
3. Заполни шаблон PR: что изменено, зачем, как проверено.
4. Дождись зелёных проверок.
5. Сделай squash-merge.
6. Удали рабочую ветку.

## Перед PR

- [ ] Ветка создана от свежего `dev`.
- [ ] Коммит оформлен по Conventional Commits.
- [ ] Документация обновлена, если изменилось поведение.
- [ ] В git не попали секреты: ключи, пароли, `.env`, backup-файлы, client links.
- [ ] Проверки из PR описаны в разделе «Как проверено».
