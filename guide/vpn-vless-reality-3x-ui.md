# Часть I. Мини-теория: что вообще такое сети

Короткий, но честный фундамент. Без него дальнейшие команды — просто заклинания.

## Клиент и сервер
Почти всё в сети — это диалог двух сторон. **Клиент** (твой телефон, ноутбук) инициирует запрос. **Сервер** (твой VPS) слушает и отвечает. VPN-сервер — это программа-сервер на арендованной машине, к которой подключаются твои клиенты.

## IP-адрес — "почтовый адрес" машины
Чтобы пакет данных дошёл, у машины должен быть адрес. **IP-адрес** — это он и есть.
- **IPv4** выглядит как `203.0.113.45` (4 числа). **IPv6** — длиннее (`2001:db8::1`), их придумали, потому что IPv4 кончаются.
- **Публичный** IP виден всему интернету (такой будет у твоего VPS). **Приватный** (`192.168.x.x`, `10.x.x.x`) живёт внутри домашней сети — поэтому у ноутбука дома обычно нет своего публичного адреса, он прячется за роутером.
- Вывод для проекта: **VPS нужен именно ради публичного IP** — точки, к которой друзья смогут подключиться из любой сети.

## Порт — "номер квартиры" на этом адресе
На одном IP крутятся десятки сервисов одновременно. Чтобы их различать, есть **порты** — номера от 1 до 65535. IP приводит пакет к нужной машине, порт — к нужной программе.
- Договорённости (well-known): **22** — SSH, **80** — HTTP, **443** — HTTPS (зашифрованный веб).
- В проекте мы ставим VLESS на **443**, чтобы он сливался с обычным HTTPS-трафиком, а MTProxy — на другой порт, потому что два сервиса один порт не делят.

## DNS — "телефонная книга" интернета
Людям удобнее имена (`vk.ru`), машинам — цифры. **DNS** переводит имя в IP. Когда ты вводишь сайт, сначала идёт DNS-запрос "какой IP у этого имени?", потом уже соединение по IP.

## Уровни сети: L3 / L4 / L7 (это важно для понимания цензуры)
Сеть устроена слоями. Упрощённо:
- **L3 (сетевой, IP)** — отвечает на вопрос "на какую *машину*". Здесь живут IP-адреса и маршрутизация.
- **L4 (транспортный, TCP/UDP)** — "к какой *программе* (порт)" и "как доставлять".
  - **TCP** — надёжный: устанавливает соединение, гарантирует доставку и порядок (веб, почта, наш VPN).
  - **UDP** — быстрый, без гарантий (видеозвонки, игры, DNS). В РФ при ограничениях UDP часто режут почти полностью — поэтому ставка на TCP.
- **L7 (прикладной)** — сам смысл: HTTP, TLS, имена сайтов.

**Зачем это знать:** фильтрация бывает на разных уровнях. Заблокировать по **IP (L3)** — грубо, но дёшево. Заглянуть внутрь и заблокировать по содержимому **(L7)** — точнее, но дороже. Российские "белые списки" работают **сразу на двух**: и по IP, и по имени сайта. Это объясняет, почему одни обходы работают, а другие нет (см. раздел про белые списки).

## TCP-рукопожатие (handshake)
Прежде чем гнать данные, TCP "здоровается": клиент шлёт **SYN**, сервер отвечает **SYN-ACK**, клиент подтверждает **ACK**. Только потом идёт обмен. DPI умеет вмешиваться прямо в этот момент (например, слать поддельный сброс соединения — RST — чтобы оборвать нежелательное подключение).

## TLS / HTTPS и магическое слово SNI
**TLS** — это шифрование поверх TCP (буква "S" в HTTP**S**). Оно прячет содержимое: провайдер видит, что ты с кем-то обмениваешься шифрованными данными, но не видит что именно.
- **Но есть дырка:** в самом начале TLS-рукопожатия клиент сообщает серверу, *на какой домен* он идёт — это поле называется **SNI (Server Name Indication)**, и оно передаётся **открыто** (исторически — чтобы один сервер мог обслуживать много сайтов).
- Именно **SNI читают цензоры**, чтобы понять, куда ты ломишься, даже не расшифровывая трафик.
- **Здесь же ключ к нашему проекту:** технологии **Reality** (для VPN) и **FakeTLS** (для MTProxy) делают так, что в SNI стоит безобидный разрешённый домен (например, `vk.ru`), а само соединение для DPI неотличимо от обычного захода на этот сайт.

## Прокси vs VPN
- **Прокси** — посредник для *конкретного* приложения/трафика. MTProxy проксирует только Telegram.
- **VPN** — туннель для *всего* трафика устройства: твои пакеты заворачиваются (инкапсулируются) и шифруются, выходят из сервера, и для внешнего мира ты как будто находишься там, где сервер.
- **Туннелирование / инкапсуляция** — это "пакет внутри пакета": твоё реальное соединение упаковано внутрь другого, которое снаружи выглядит безобидно.

## DPI и ТСПУ — кто и как фильтрует
**DPI (Deep Packet Inspection)** — оборудование, которое смотрит не только адреса, но и "вглубь" пакетов: распознаёт протоколы по сигнатурам, читает SNI, считает объёмы. В РФ это **ТСПУ** — техсредства, стоящие у операторов. Наш проект учит обходить *обычный* DPI (камуфляж под TLS), но честно упирается в предел при полном "белом списке" (см. ниже) — и это само по себе полезный урок про границы возможного.

# Часть II. Сборка проекта

Дальше — практика. По задумке ты идёшь сюда вместе с Claude Code, который объясняет каждый шаг по правилам из раздела 0.

> **Честно про реальность.** Обход блокировок — игра в кошки-мышки. Reality + Vision сейчас проходит ТСПУ, но вечной гарантии нет: периодически прилетают новые сигнатуры и баны IP. Поэтому в проект заложены **запасной протокол** и **подписки**, чтобы быстро переехать без перенастройки у друзей.

## Шаг 0. Выбор VPS
- **Характеристики:** 1 ядро CPU, 1 ГБ RAM, 10 ГБ диска — хватает на 10–50 человек. ~$3–5/мес.
- **Локация:** ближе к РФ = меньше пинг. Германия, Финляндия, Нидерланды.
- **ОС:** Ubuntu 22.04 или Debian 12.
- **Репутация IP важна.** ТСПУ банит и по IP. Бери провайдера/IP "посвежее" и будь готов переехать на новый IP при бане.

После создания дадут IP и root-доступ:
```bash
ssh root@SERVER_IP
```
> 💡 **Чему учит:** что такое публичный IP и зачем он нужен; SSH как защищённый удалённый доступ к серверу (хлеб DevOps). Концепция: клиент–сервер, L3-адресация.

## Шаг 1. Ansible-bootstrap и базовая защита сервера
Первый этап больше не делаем набором ручных команд. Его кодифицирует Ansible:
playbook создаёт пользователя `mirage`, добавляет SSH-ключ, включает `ufw`,
ставит `fail2ban`, бэкапит административные файлы и только после проверки ключа
отключает парольный вход.

Почему так безопаснее: SSH-hardening легко сделать слишком рано и потерять доступ
к серверу. Playbook делит работу на два этапа: сначала новый вход по ключу, потом
отключение пароля с rollback-таймером.

Полный порядок действий — в [runbook для Ansible-bootstrap](../docs/runbooks/bootstrap-vps-ansible.md).
Короткий маршрут на сервере:

```bash
apt update
apt install -y ansible git
git clone --branch dev https://github.com/duckduckduck1/Mirage.git /root/mirage
cd /root/mirage/infra/ansible
ansible-playbook --syntax-check site.yml
ansible-playbook site.yml
```

После первого запуска проверь новый вход с локальной машины:

```bash
ssh -i ~/.ssh/mirage_ed25519 mirage@SERVER_IP
```

Затем включи SSH-hardening:

```bash
ansible-playbook site.yml -e enable_ssh_hardening=true --tags hardening
```

Контрольные проверки на сервере:

```bash
sudo -n true
sudo ufw status
sudo /usr/sbin/sshd -T | grep -E 'passwordauthentication|kbdinteractiveauthentication|permitrootlogin|pubkeyauthentication'
```

Ожидаемый результат: `passwordauthentication no`, `pubkeyauthentication yes`,
`ufw` активен, а порты `22/tcp`, `443/tcp`, `8388/tcp` открыты.
Порт веб-панели добавим после установки (он будет случайным).

> 💡 **Чему учит:** управлению конфигурацией, идемпотентности и безопасному
> hardening. Ты не просто вводишь команды, а описываешь желаемое состояние сервера
> и проверяешь его диагностикой.

Вопросы для самопроверки:

- Почему парольный вход отключаем только после проверки входа по ключу?
- Зачем playbook делает бэкап `/etc/ssh`, `/etc/sudoers*` и `/etc/ufw` перед изменениями?

## Шаг 2. Установка панели 3x-ui

3x-ui — веб-интерфейс над Xray-core: пользователи, лимиты, QR-коды, ссылки,
подписки и статистика. Это удобно, но панель нельзя светить в интернет: она
управляет всем VPN-сервисом.

Полный повторяемый порядок действий — в [runbook по 3x-ui и VLESS Reality](../docs/runbooks/setup-xui-vless-reality.md).
Короткий маршрут на VPS:

```bash
curl -Ls https://raw.githubusercontent.com/MHSanaei/3x-ui/master/install.sh -o /tmp/3x-ui-install.sh
sudo bash /tmp/3x-ui-install.sh
```

Во время установки выбери:

- **Database Selection** → `SQLite` для маленького учебного сервера. PostgreSQL
  допустим, но усложняет бэкап.
- **Panel Port** → случайный порт `10000–60000`, не `22`, не `443`, не `8388`.
- **Username** и **Password** → сильные значения, не `admin/admin`.
- **WebBasePath** → случайный секретный путь.
- **SSL Certificate Setup** → **Skip SSL**, потому что панель будет доступна
  через SSH-туннель.
- **Bind the panel to 127.0.0.1 only?** → `y`.

Если случайно ответил не `y`, исправь после установки:

```bash
sudo /usr/local/x-ui/x-ui setting -listenIP 127.0.0.1
sudo systemctl restart x-ui
```

Порт панели в `ufw` не открывай. Панель должна слушать только localhost:

```bash
sudo ss -tlnp | grep 'ПОРТ_ПАНЕЛИ'
```

Ожидаемый признак:

```text
127.0.0.1:ПОРТ_ПАНЕЛИ
```

С локальной машины открой SSH-туннель:

```powershell
ssh -N -i $HOME\.ssh\mirage_ed25519 -L 2096:127.0.0.1:ПОРТ_ПАНЕЛИ mirage@SERVER_IP
```

Пока туннель открыт, зайди в панель:

```text
http://localhost:2096/WEB_BASE_PATH
```

`WEB_BASE_PATH` возьми из вывода установки или из файла
`/etc/x-ui/install-result.env`. Этот файл содержит секреты, поэтому не копируй
его в git и не отправляй в чат.

> 💡 **Чему учит:** установка и запуск systemd-сервиса; **SSH-туннель** (`-L`) —
> это безопасный проброс локального порта к закрытому порту на сервере. Так ты
> оставляешь админку доступной себе, но не публикуешь её в интернет.

- Почему порт панели не нужно открывать в `ufw`?
- Чем отличается порт панели `ПОРТ_ПАНЕЛИ` от VPN-порта `443`?

## Шаг 3. Основной inbound — VLESS + Reality

Inbound — это входная точка Xray: какой порт слушать, каким протоколом принимать
клиента и как маскировать соединение.

В панели открой **Входящие** → **Создать подключение**.

На вкладке **Основное**:

| Поле | Значение |
|---|---|
| **Включить** | включено |
| **Примечание** | `vless-reality-vision` |
| **Протокол** | `vless` |
| **Адрес** | пусто, чтобы слушать все адреса |
| **Стратегия адреса для ссылок** | публичный IP сервера или пользовательский адрес |
| **Адрес для ссылок** | `SERVER_IP`, если поле появилось |
| **Порт** | `443` |
| **Общий расход** | `0` |
| **Сброс трафика** | **Никогда** |
| **Дата окончания** | пусто |

Поле **Адрес** отвечает за прослушивание. Его можно оставить пустым, чтобы Xray
слушал публичный интерфейс. А **адрес для ссылок** нужен клиентам: если его не
указать, Hiddify может показать **Неизвестный IP** и профиль не подключится.

На вкладке **Протокол**:

| Поле | Значение |
|---|---|
| **Расшифрование** | `none` |
| **Шифрование** | `none` |

На вкладке **Поток**:

| Поле | Значение |
|---|---|
| **Транспорт** | `RAW` |
| **Proxy Protocol** | выключено |
| **HTTP Обфускация** | выключено |
| **Sockopt** | выключено |
| **TCP Masks** | не добавлять |

На вкладке **Безопасность** выбери **Reality**:

| Поле | Значение |
|---|---|
| **Xver** | `0` |
| **uTLS** | `chrome` |
| **Цель** | `vk.ru:443` |
| **SNI** | `vk.ru` |
| **Макс. разница во времени (мс)** | `0` |
| **Short IDs** | один сгенерированный short ID |
| **SpiderX** | `/` |
| **Публичный ключ** | сгенерировать |
| **Приватный ключ** | сгенерировать и не раскрывать |
| **mldsa65 Seed / Verify** | пусто |
| **Лог мастер-ключей** | пусто |

`Цель` и `SNI` должны совпадать по домену. Приватный ключ Reality остаётся на
сервере. Клиент получает только публичный ключ в `vless://`-ссылке.

После сохранения проверь, что Xray слушает `443`:

```bash
sudo ss -tlnp | grep ':443'
sudo ufw status
systemctl status x-ui --no-pager
```

> 💡 **Чему учит:** самое ядро проекта — **SNI и TLS-камуфляж**. Ты на практике
> видишь, как соединение к твоему VPS выглядит для DPI как обычный HTTPS к
> разрешённому сайту. Концепция: L7, TLS-рукопожатие, active probing.

Вопросы для самопроверки:

- Почему `Цель` и `SNI` должны совпадать?

## Шаг 4. Клиенты и Hiddify

Правило: **один клиент = один человек или одно устройство**. Так проще смотреть
статистику, отключать доступ и менять параметры без влияния на остальных.

Если в колонке **Клиенты** у inbound стоит `0`, создай клиента:

1. Открой **Клиенты**.
2. Нажми **Добавить клиента**.
3. На вкладке **Основные** укажи:

   | Поле | Значение |
   |---|---|
   | **Email** | `main`, `phone` или имя пользователя |
   | **Лимит трафика (ГБ)** | `0` |
   | **Лимит IP** | `0` |
   | **Срок действия** | пусто |
   | **Привязанные входящие** | `vless-reality-vision` |
   | **Включить** | включено |

4. На вкладке **Учетные данные** проверь:

   | Поле | Значение |
   |---|---|
   | **UUID** | сгенерирован |
   | **Flow** | `xtls-rprx-vision` |

5. Нажми **Создать**.

Во **Входящих** в колонке **Клиенты** должно стать `1`.

Для первого теста экспортируй одиночный профиль:

1. В строке inbound нажми меню **⋮**.
2. Выбери **Экспорт подключений**.
3. Раскрой профиль **Vless / TCP / REALITY**.
4. Скопируй ссылку `vless://...`.

Не отправляй ссылку в чат. Проверь её локально в текстовом редакторе:

```text
vless://
@SERVER_IP:443
security=reality
type=tcp
flow=xtls-rprx-vision
sni=vk.ru
fp=chrome
pbk=
sid=
```

В Hiddify добавь профиль через clipboard или ручной импорт. Если видишь
`unable to determine config format`, ты скопировал не одиночный `vless://`
профиль. Если видишь timeout, проверь с локальной машины:

```powershell
Test-NetConnection SERVER_IP -Port 443
```

Если `TcpTestSucceeded : True`, но Hiddify не подключается, проверь адрес в
профиле. Симптом **Неизвестный IP** означает, что в экспортированной ссылке нет
`SERVER_IP`.

> 💡 **Совет про подписку (важно для DevOps-мышления):** для первого теста
> используй одиночный `vless://` профиль. Когда дойдёшь до домена и миграции,
> раздавай **subscription-ссылку**, а не голый конфиг. Тогда при смене сервера/IP
> ты правишь только свою сторону, а друзья получают обновление автоматически.

## Шаг 5. Запасной протокол — Shadowsocks-2022
Чтобы при блокировке Reality не остаться без связи — добавь **второй inbound**:
- **Protocol:** Shadowsocks · **Port:** напр. 8388
- **Method:** `2022-blake3-aes-256-gcm` (альтернатива: `chacha20-ietf-poly1305`)
- добавь тех же клиентов.

Идея "швейцарского ножа": прижали один протокол днём — друзья в один тап переключаются на другой профиль.
> 💡 **Чему учит:** **резервирование / отказоустойчивость** (redundancy) — базовый принцип SRE: не держать единую точку отказа.

## Telegram через свой MTProxy (маскировка под vk.ru)
Отдельный компонент. MTProto-прокси нужен, когда Telegram **замедляют** (в РФ регулярно). Инструмент — **mtg** (9seconds/mtg, v2), режим **FakeTLS**: трафик заворачивается в TLS, и прокси прозрачно проксирует настоящий vk.ru. Для DPI — обычный визит на ВКонтакте.

### Установка (Docker)
```bash
curl -fsSL https://get.docker.com | sh        # Docker, если ещё нет

# 1. FakeTLS-секрет с маскировкой под vk.ru
docker run --rm nineseconds/mtg:2 generate-secret vk.ru
# выдаст строку вида ee<...> — сохрани её
```
`config.toml`:
```toml
secret = "ee...вставь_секрет..."
bind-to = "0.0.0.0:3128"
```
Запуск (на хосте порт **8443**, чтобы не конфликтовать с VLESS на 443):
```bash
docker run -d \
  -v $PWD/config.toml:/config.toml \
  -p 8443:3128 \
  --name mtg-proxy \
  --restart=unless-stopped \
  nineseconds/mtg:2

ufw allow 8443/tcp
```
> Разбор флагов (попроси Claude Code объяснить, если непонятно): `-d` — запуск в фоне (detached); `-v ИСХОДНИК:ЦЕЛЬ` — пробросить файл конфига внутрь контейнера; `-p 8443:3128` — внешний порт 8443 → внутренний 3128; `--restart=unless-stopped` — поднимать контейнер после перезагрузки.

### Ссылка для друзей
```bash
docker exec mtg-proxy /mtg access /config.toml
```
Вернёт `tg://proxy?...`, `https://t.me/proxy?...` и QR. Друг открывает ссылку → Telegram сам предложит подключить прокси.

### Нюансы
- Домен маскировки обязан быть **доступен в РФ** — vk.ru/vk.com идеально (он в белом списке). Никогда не бери для FakeTLS заблокированный домен.
- **443 занят** под VLESS на том же IP. Два "псевдо-TLS" сервиса на одном порту одного IP не уживутся. Варианты: MTProxy на отдельном порту (8443, как выше); либо второй IP у провайдера и MTProxy на 443 второго IP; либо (продвинуто) **SNI-роутер** на 443, раздающий соединения по домену.
- IP прокси — расходник: забанили → новый сервер, новый секрет.
- Один секрет можно раздать нескольким; нужны отдельные секреты на каждого — есть форк mtg с multi-secret (dolonet).
> 💡 **Чему учит:** Docker на реальном примере (образ, контейнер, тома, проброс портов, restart policy); снова **SNI-камуфляж**, но для другого протокола; конфликт портов — наглядный урок про "один порт = один слушатель на IP".

## Про белые списки в РФ — что реально работает (честно)
Это надо понимать, чтобы не было ложных ожиданий — и это сам по себе важный урок про пределы технологий.

«Белые списки» — режим **drop-all**: пропускается только одобренное, остальное режется. Механизм **другой**, чем обычные блокировки.

1. **Пока это только мобильный интернет** (МТС, МегаФон, Билайн, Т2). Домашний Wi-Fi / проводной под белые списки **не попадает** — там обычная блокировка по чёрному списку, и твой VLESS+Reality с MTProxy работают штатно.
2. **Фильтрация двухуровневая: по IP (L3) + по SNI (L7).** В белом списке ~63 тыс. IP из 46 млн (≈0,1%).
3. **Главное:** в drop-all VPN/прокси на зарубежном VPS **не проходит**. Причина — проверка по **IP**: твой сервер не в списке, и подмена SNI на vk.ru **не спасает**, потому что IP-проверка срабатывает раньше домена. Это фундаментальное ограничение self-hosting — выбором домена не обойти. (Вот зачем мы учили L3 vs L7: теперь понятно, *почему* именно.)
4. **Что реально пробивает drop-all:** только хрупкие трюки через инфраструктуру из списка (relay через TURN-серверы VK/Яндекса) — их быстро патчат, на стабильную раздачу не годятся. Практика: при полном drop-all — переключаться на **домашний Wi-Fi**.

**Что даёт маскировка под VK:** помогает в **обычном** режиме DPI — трафик сливается с разрешённым, меньше шансов на SNI-блок и детект протокола (особенно для Telegram). Полный белый список это **не** пробивает.

Итого по сценариям:
- **Домашний Wi-Fi** — всё работает всегда.
- **Мобильный, обычный режим** — работает; маскировка под VK помогает.
- **Мобильный, drop-all (отключения)** — зарубежный VPS не проходит, спасает только Wi-Fi.

# Глоссарий

- **VPN** — туннель для всего трафика устройства: твои пакеты шифруются и выходят через сервер.
- **VPS** — арендованный виртуальный сервер с публичным IP.
- **IP-адрес** — адрес машины в сети (L3).
- **Порт** — номер сервиса на машине (L4); 1–65535.
- **DNS** — перевод имён (`vk.ru`) в IP.
- **TCP / UDP** — транспорт: TCP надёжный с соединением, UDP быстрый без гарантий.
- **TLS / HTTPS** — шифрование поверх TCP; прячет содержимое, но не SNI.
- **SNI** — открытое поле в начале TLS с именем сайта; его читают цензоры.
- **Прокси** — посредник для конкретного приложения (наш MTProxy — для Telegram).
- **Xray-core** — движок, реализующий протоколы (VLESS и др.).
- **VLESS** — лёгкий протокол передачи поверх Xray.
- **Reality** — технология TLS-камуфляжа: соединение выглядит как обычный заход на реальный сайт.
- **XTLS-Vision (Flow)** — режим, усиливающий стойкость к активному зондированию DPI.
- **Shadowsocks** — другой протокол-обфускатор; у нас как резерв.
- **MTProxy** — родной прокси-протокол Telegram.
- **FakeTLS** — режим MTProxy, заворачивающий трафик в TLS под видом заданного домена.
- **DPI** — глубокая инспекция пакетов (анализ содержимого, не только адресов).
- **ТСПУ** — российское DPI-оборудование у операторов.
- **drop-all / белый список** — режим "разрешено только из списка, остальное блок".
- **SSH** — защищённый удалённый доступ к серверу; `-L` — проброс порта через туннель.
- **ufw / iptables** — фаервол Linux (что пускать по портам).
- **fail2ban** — автобан тех, кто перебирает пароли.
- **Docker / контейнер / образ / том** — упаковка и изолированный запуск сервиса; образ — шаблон, контейнер — запущенный экземпляр, том (`-v`) — проброс данных внутрь.
- **systemd / демон** — система управления фоновыми сервисами в Linux; `journalctl` — их логи.
- **Reverse proxy / SNI-роутер** — сервис, раздающий входящие соединения по домену/маршруту.
- **Let's Encrypt / ACME** — бесплатные TLS-сертификаты и протокол их автополучения.

# Часть III. Как прокачать проект (для резюме и собеседования)

Базовый проект уже хорош. Эти расширения превращают его в сильный кейс DevOps/SRE. Делай по одному — каждое даёт отдельную тему для собеседования.

1. **Infrastructure as Code — Terraform.** Описать сам VPS кодом: провайдер, регион, размер, firewall-правила. `terraform apply` поднимает сервер с нуля. → *"Провижининг инфраструктуры через Terraform, декларативное описание ресурсов"*.
2. **Configuration Management — Ansible.** Расширить текущий bootstrap playbook: добавить установку и настройку 3x-ui, mtg, `ufw`, `fail2ban` — идемпотентно и воспроизводимо. → *"Автоматизация конфигурации серверов через Ansible, идемпотентные плейбуки"*.
3. **Docker Compose.** Собрать весь стек (3x-ui + mtg + мониторинг) в один `docker-compose.yml`. → *"Оркестрация многоконтейнерных приложений через Docker Compose"*.
4. **Observability — Prometheus + Grafana.** mtg отдаёт метрики Prometheus из коробки; добавь `node_exporter` для метрик хоста (CPU, сеть, диск) и собери дашборд в Grafana. → *"Сбор метрик (Prometheus), визуализация (Grafana), мониторинг сетевого сервиса"*.
5. **Алертинг — Alertmanager.** Уведомление в тот же Telegram, если прокси упал, кончилось место или скакнул трафик. → *"Настройка алертов, проактивный мониторинг (SRE)"*.
6. **CI/CD — GitHub Actions.** Линт/валидация конфигов и Terraform-плана на каждый push, автодеплой. → *"CI/CD-пайплайны, автоматизация доставки"*.
7. **Надёжность по-SRE.** Сформулировать SLO (например, аптайм 99.5%), сделать health-check, бэкап БД панели, резервный сервер с авто-переключением, написать runbook на инцидент "сервер забанили". → *"Определение SLO/SLI, runbooks, отказоустойчивость, бэкапы"*.
8. **Security hardening.** SSH только по ключам (отключить пароль), управление секретами, аудит. → *"Hardening, SSH key-based auth, управление секретами"*.

> Каждый пункт — это и навык, и история на собеседовании в формате "была задача → что сделал → какой принцип за этим".
