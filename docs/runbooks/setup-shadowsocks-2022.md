# Проверка Shadowsocks-2022

Runbook описывает диагностическую проверку inbound `Shadowsocks-2022` в 3x-ui.
Shadowsocks-2022 не входит в текущую production-схему Mirage. Используй этот
runbook только как отдельный эксперимент после backup.

Текущий production-checkpoint описан отдельно:

- [Production-checkpoint VLESS Reality](vless-production-checkpoint.md)

Команды на VPS выполняй под пользователем `mirage`. Реальные IP, `ss://`-ссылки,
пароли, ключи, UUID, API-токены и backup-файлы не добавляй в git.

## Перед началом

Проверь рабочее состояние базового сервиса:

```bash
sudo -n true
sudo ufw status
sudo ss -tlnp | grep -E ':443|:8388|:ПОРТ_ПАНЕЛИ'
systemctl status x-ui --no-pager
```

Ожидаемо до включения тестового inbound:

```text
*:443                         xray-linux-amd64
127.0.0.1:ПОРТ_ПАНЕЛИ          x-ui
22/tcp                        ALLOW
443/tcp                       ALLOW
x-ui active (running)
```

На этом этапе `8388/tcp` не должен слушать и не должен быть открыт в `ufw`. Если
`8388/tcp` уже слушает другой процесс, остановись и разберись, что заняло порт:

```bash
sudo ss -tlnp | grep ':8388'
```

Перед добавлением inbound сделай свежий бэкап 3x-ui:

- [Бэкап 3x-ui](backup-xui.md)

Затем временно открой порт для проверки:

```bash
sudo ufw allow 8388/tcp
```

## Генерация ключа

Для Shadowsocks-2022 нужен сильный ключ. Если панель умеет генерировать ключ
сама, используй генератор панели. Если нужен ручной ввод, сгенерируй ключ на VPS:

```bash
openssl rand -base64 32
```

Сохрани значение в менеджере паролей. Не используй пароль панели, SSH-ключ,
UUID VLESS или старые клиентские секреты.

## Создание inbound

Открой панель 3x-ui через SSH-туннель:

```powershell
ssh -N -i $HOME\.ssh\mirage_ed25519 -L 2096:127.0.0.1:ПОРТ_ПАНЕЛИ mirage@SERVER_IP
```

В браузере открой:

```text
http://localhost:2096/WEB_BASE_PATH
```

В панели открой **Входящие** и нажми **Создать подключение**.

На вкладке **Основное**:

| Поле | Значение |
|---|---|
| **Включить** | включено |
| **Примечание** | `shadowsocks-2022-reserve` |
| **Протокол** | `shadowsocks` |
| **Адрес** | пусто, чтобы слушать все адреса |
| **Стратегия адреса для ссылок** | публичный IP сервера или пользовательский адрес |
| **Публичный адрес / адрес для ссылок** | `SERVER_IP` или `vpn.ДОМЕН`, если домен уже настроен |
| **Порт** | `8388` |
| **Общий расход** | `0` |
| **Сброс трафика** | **Никогда** |
| **Дата окончания** | пусто |

На вкладке **Протокол**:

| Поле | Значение |
|---|---|
| **Method** | `2022-blake3-aes-256-gcm` |
| **Password / Key** | новый сгенерированный ключ |
| **Network** | `tcp`, если поле доступно |

Для первого теста используй `tcp`. UDP можно добавить отдельным изменением, когда
будет понятен сценарий использования и обновлены правила `ufw`.

Если панель создаёт Shadowsocks через клиента, добавь клиента:

| Поле | Значение |
|---|---|
| **Email** | `ss-main` или имя устройства |
| **Лимит трафика (ГБ)** | `0` |
| **Лимит IP** | `0` |
| **Срок действия** | пусто |
| **Привязанные входящие** | `shadowsocks-2022-reserve` |
| **Включить** | включено |

Нажми **Создать** или **Сохранить**.

Если 3x-ui показывает и общий ключ inbound, и ключ клиента, сгенерируй два разных
ключа. Для `2022-blake3-aes-256-gcm` каждый ключ генерируй командой
`openssl rand -base64 32`.

## Проверка на VPS

Проверь, что Xray слушает `8388/tcp`:

```bash
sudo ss -tlnp | grep ':8388'
```

Ожидаемый признак:

```text
*:8388                    xray-linux-amd64
```

Проверь firewall:

```bash
sudo ufw status
```

Ожидаемый минимум:

```text
22/tcp                    ALLOW
443/tcp                   ALLOW
8388/tcp                  ALLOW
```

Проверь сервис:

```bash
systemctl status x-ui --no-pager
```

Если порт не появился, открой логи:

```bash
sudo journalctl -u x-ui -n 80 --no-pager
```

Исправь ошибку в inbound и сохрани конфигурацию ещё раз.

## Проверка с локальной машины

С Windows проверь доступность порта:

```powershell
Test-NetConnection SERVER_IP -Port 8388
```

Ожидаемый результат:

```text
TcpTestSucceeded : True
```

Если используешь домен и он уже настроен:

```powershell
Test-NetConnection vpn.ДОМЕН -Port 8388
```

## Экспорт профиля

В строке inbound нажми меню **⋮** и выбери экспорт профиля или QR-код клиента.
Скопируй одиночную ссылку `ss://...`.

Перед импортом проверь ссылку в локальном текстовом редакторе. В ней должны быть
признаки протокола и порта:

```text
ss://
SERVER_IP:8388
```

Если уже настроен домен, ожидаемый адрес:

```text
vpn.ДОМЕН:8388
```

Если адрес и порт скрыты внутри base64-части ссылки, проверь их в окне экспорта
3x-ui до копирования.

Не передавай ссылку во внешние каналы. Она содержит секрет подключения.

## Импорт в Hiddify

1. Открой Hiddify.
2. Добавь профиль из clipboard или через QR-код.
3. Выбери профиль `shadowsocks-2022-reserve`.
4. Подключись.
5. Открой тестовый сайт или YouTube.
6. Вернись в 3x-ui и проверь, что трафик растёт у Shadowsocks inbound.

Если Hiddify пишет `unable to determine config format`, скопирована не одиночная
`ss://`-ссылка. Вернись в экспорт клиента и скопируй именно профиль подключения.

## Диагностика

### Порт недоступен

Проверь:

```bash
sudo ss -tlnp | grep ':8388'
sudo ufw status
systemctl status x-ui --no-pager
```

Если `ss` не показывает `*:8388`, inbound не применился. Сохрани inbound заново
или перезапусти Xray из панели.

Если `ss` показывает порт, но `Test-NetConnection` не проходит, проверь `ufw` и
панель провайдера VPS. Некоторые провайдеры имеют внешний firewall.

### Клиент импортируется, но не подключается

Проверь:

- метод ровно `2022-blake3-aes-256-gcm`;
- ключ не менялся после экспорта;
- ссылка содержит правильный адрес и порт;
- клиент поддерживает Shadowsocks-2022;
- в 3x-ui нет ошибки применения конфигурации.

### Нужно UDP

Текущий этап использует только `8388/tcp`. Если нужен UDP relay, делай это
отдельной задачей:

1. Обнови Ansible-bootstrap и `ufw` для `8388/udp`.
2. Включи UDP в inbound.
3. Проверь `sudo ss -ulnp | grep ':8388'`.
4. Проверь клиент.
5. Обнови документацию и бэкап.

## После проверки

1. Сделай новый бэкап 3x-ui.
2. Сохрани `ss://`-ссылку или QR-код в менеджере паролей.
3. Проверь, что VLESS Reality продолжает работать.
4. Проверь, что в подписку или ручную выдачу попадут оба профиля:

   ```text
   VLESS Reality          :443
   Shadowsocks-2022       :8388
   ```

Если тест не подтвердился, выключи inbound и закрой порт:

```bash
sudo ufw delete allow 8388/tcp
sudo ss -tlnp | grep ':8388' || true
```
